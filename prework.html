Set up Confluent Cloud

You will set up the four things the lab needs: an environment, a Kafka cluster, a topic, and a Flink compute pool. Nothing streams yet, so this costs almost nothing.

About 30 minutesBrowser onlyNo coding

What you'll set up

Here is what you will have at the end:

Two rules
  • Use exactly these names. The lab uses them in its SQL.
  • Put the cluster and the compute pool in the same cloud provider and region. Pick one near you and use it for both.

1. Create an account

5 minutes
  1. Go to confluent.cloud and sign up (or sign in if you already have an account).
  2. New accounts get free trial credit for 30 days. You may still need to add a payment method or a promo code before you can create anything. You do this under Billing & payment.
  3. If a guided setup starts, skip it. You will follow the steps below instead.
Check

2. Open the default environment

1 minute

You don't need to create an environment. Every Confluent Cloud account comes with one called default, and you'll use it for the whole lab.

  1. In the left menu, click Environments.
  2. Open default.
  3. If you're asked to choose a Stream Governance package at any point, choose Essentials. This gives you the Schema Registry, which Flink needs.
Check

3. Create a Kafka cluster

5 minutes (mostly waiting)
  1. In the default environment, click Add cluster (or Create cluster).
  2. Choose Basic.
  3. Pick a cloud provider and region. Write them down: you need the same ones in step 5.
  4. Name it orders-cluster and click Launch cluster. It takes a few minutes to be ready.
Check

4. Create a topic

2 minutes

A topic is a named stream of messages. Orders will flow into this one during the lab.

  1. Open orders-cluster, go to Topics, and click Create topic.
  2. Name it orders. Leave the number of partitions at the default.
  3. Click Create with defaults. If it asks you to define a data contract, click Skip. The data generator will add one during the lab.
Don't start the data generator yet

You'll start it at the beginning of the lab so that nothing runs, or costs money, before then.

Check

5. Set up a Flink compute pool

5 minutes

A compute pool is the processing power that runs your SQL. You only pay while a query is running.

  1. Go back to the default environment and open the Flink tab.
  2. Click Create compute pool.
  3. Choose the same cloud and region as your cluster.
  4. Name it workshop-pool. For Max CFUs, pick the smallest option. That is plenty for this lab.
  5. Click Create and wait until it says Running.
Already have a compute pool in that region?

Don't create a second one. Rename the one you have to workshop-pool in its settings, then check that it says Running.

Check

6. Check it works

5 minutes
  1. On the compute pool, click Open SQL workspace.
  2. At the top of the workspace, set Use catalog to default and Use database to orders-cluster.
  3. Paste each statement below into a cell and click Run. Run them one at a time.
SHOW CATALOGS;
SHOW DATABASES;
SHOW TABLES;
What should I see?

SHOW CATALOGS lists default. SHOW DATABASES lists orders-cluster. SHOW TABLES lists orders.

Notice that you never created a table. Flink turns every Kafka topic into a table automatically: environment = catalog, cluster = database, topic = table. You'll use this idea throughout the lab.

Don't query orders yet

It has no data or schema until you start the generator in the lab.

Check

Optional: batch, micro-batch and stream processing

Optional background reading. You don't need it to complete the pre-work or the lab.

Almost all business data starts life as a stream of events: an order is placed, a card is swiped, a sensor reports a value, a user clicks. The question is how quickly you process those events once they happen.

The same events processed three ways. Each step down shrinks the wait between an event happening and a result being available.

Batch processing

For decades, data was processed in batch jobs: collect everything for a day (or a week), then run one big job over it. A batch job works on bounded data, with a known start and end, so it can read everything before it produces an answer.

That has two problems. Results are always hours or days old. And a failure is expensive: if a job that takes 13 hours fails in hour 12, there may not be enough time left in the day to run it again. The usual fix was to make batches smaller: hourly instead of daily.

Micro-batching

Keep shrinking the batches, to minutes and then seconds, and you get micro-batching. Results arrive much sooner, and a failure only affects a small batch. But every result still waits for its batch to fill and be scheduled, and work that spans batches (like a running total per customer) has to be carried from one batch to the next.

Taken to its natural end, a batch holds just one event. At that point there's no reason to batch at all.

Stream processing

Stream processing handles each event as it arrives. The data is unbounded: it has a start but no end. Events flow through a chain of processing steps (operators), and each step passes its result straight on to the next.

Two things make this hard, and Apache Flink is built for both:

  • State. Events are rarely independent. Counting orders per item, spotting a second login from another country, or matching a payment to its order all need memory of earlier events. Keeping that memory in an external database is slow at scale, so Flink keeps state next to the processing and saves it regularly (checkpoints) so it can recover from failures without losing or double-counting anything.
  • Time. Events can arrive late or out of order. A stream processor needs to know which time an event belongs to and when it has seen enough to give an answer. You'll meet this as event time and watermarks.

Why streaming matters

NeedExample
Act while it still mattersBlock a fraudulent payment before it completes, not in tomorrow's report.
Meet user expectationsPeople expect a comment, an order status or a price to update immediately.
Keep systems in syncInventory, search indexes and dashboards change the moment an order is placed.
Process data once, continuouslyInstead of rerunning a job over all of yesterday's data, update the result with each new event.

In this lab, a stream of online orders flows into Apache Kafka, and you'll use Flink SQL to process it continuously: plain SQL, running as a stream-processing job.
